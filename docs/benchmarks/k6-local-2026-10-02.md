## Workload and Environment

- The script created a `compute_checksum` job with `work_factor: 1` and fetched it for every iteration; it listed pending jobs once every five iterations.
- The API used its current configuration: five workers, adaptive scheduler polling, batch size 50, and a 1-second fallback poll interval.
- The API ran on the Windows host at `localhost:8080`; PostgreSQL ran in an isolated, no-volume Docker container on host port 5435. Both ran on the same machine.
- OS: Windows 11 Pro 10.0.26200, 64-bit.
- CPU: 12th Gen Intel Core i5-1245U, 10 cores / 12 logical processors.
- Visible RAM: 15.6 GiB.
- PostgreSQL: 16.15. Docker server: 29.7.2. Go: 1.27.0. k6: 2.3.0.
- Base revision: `cab3943`. The working tree also contained the k6 authentication change and the ULID concurrency fix/test; this run was not made from a clean commit.

## Reproduction

From the repository root, set `ORCHESTRIX_API_KEY` to a test-server API key and run:

```powershell
k6 run `
  -e "API_KEY=$env:ORCHESTRIX_API_KEY" `
  -e BASE_URL=http://localhost:8080 `
  -e MAX_VUS=100 `
  -e RAMP_DURATION=15s `
  -e HOLD_DURATION=45s `
  --summary-export=k6-summary.json `
  loadtest/api_load_test.js
```

Use a disposable database. The API key used for this run was generated for the local benchmark and is not recorded here.

## Caveats

This is one run on a single developer machine; the listed percentiles are across requests within that run, not across repeated runs. The result should not be described as a maximum, production capacity, scheduler-only throughput, or throughput over a 1-million-row table.

An initial pre-fix run had 136 create failures due to duplicate ULIDs. The shared `ulid.Monotonic` entropy source was not safe for concurrent use. The generator now wraps it with `ulid.LockedMonotonicReader`; the concurrent uniqueness regression test passed before this measured rerun. The final run had zero duplicate-key errors.
